# 3x-ui Migration Manager v2.2 (release candidate)

**Резервное копирование и перенос готовой конфигурации 3x-ui между VPS** — с русскоязычным меню, зашифрованным архивом и определением IP нового сервера.

[![Ubuntu / Debian](https://img.shields.io/badge/OS-Ubuntu%20%2F%20Debian-blue)](https://ubuntu.com/) [![Версия](https://img.shields.io/badge/версия-2.2--rc-2274A5)](https://github.com/djekk9-ops/3XUI-MIGRATION) [![GitHub](https://img.shields.io/badge/репозиторий-GitHub-181717?logo=github)](https://github.com/djekk9-ops/3XUI-MIGRATION)

> [!IMPORTANT]
> **Это инструмент переноса, а не создания VPN с нуля.** Чтобы получить на новом VPS существующие подключения, сначала создайте резервную копию работающей 3x-ui на старом сервере.
>
> Исходная версия v2.1 была проверена на новом VPS (WebSocket, Reality, Hysteria2), но потребовала ручных исправлений SQLite и Nginx. Для v2.2 нужен повторный полный тест на чистом VPS. Не отключайте старый VPS до проверки нового.

## 1. Возможности и ограничения

Менеджер предназначен для копирования **фактических настроек, находящихся в SQLite-базе** `/etc/x-ui/x-ui.db`, а не для самостоятельного создания новых профилей.

- Создаёт согласованную копию SQLite-базы работающей панели.
- Сохраняет конфигурацию Nginx (если есть), каталог `/etc/letsencrypt` и отдельные каталоги сертификатов.
- Шифрует архив с помощью **GPG / AES-256** и запрашивает отдельный пароль.
- Определяет публичный IPv4 и основной сетевой интерфейс исходного и нового VPS.
- На новом сервере изменяет **только распознанные адресные поля** базы и подготавливает Nginx для проверки.
- Сохраняет клиентские UUID, пароли и приватные ключи без автоматической замены.
- Предоставляет отдельную диагностику DNS, TLS, портов и служб.

### Примеры переносимых подключений

| Протокол | Транспорт |
| --- | --- |
| VLESS | XHTTP + TLS |
| VLESS | WebSocket + TLS |
| VLESS | TCP + Reality |
| VLESS | HTTPUpgrade + TLS |
| Trojan | TCP + TLS |
| Hysteria 2 | UDP + TLS |
| AmneziaWG | UDP |
| Shadowsocks 2022 | TCP + UDP |

Количество перенесённых подключений определяется содержимым базы, а не этой таблицей. Работу каждого протокола и его совместимость с версией Xray нужно проверить после переноса.

> [!NOTE]
> Менеджер **не изменяет DNS у регистратора**, **не настраивает CDN**, **не переключает подписки в клиентах автоматически**, **не открывает порты у VPS-провайдера** и **не гарантирует продление перенесённых сертификатов**. Смена домена на другой также не автоматизирована: восстановление предполагает прежнее доменное имя (`--same-domain`).

## 2. Требования

**Исходный VPS:** Ubuntu/Debian, рабочая 3x-ui с SQLite-базой `/etc/x-ui/x-ui.db`, доступ root по SSH.

**Новый VPS:** чистая Ubuntu (например, 24.04 LTS) или Debian, публичный IPv4, доступ root, свободные нужные TCP/UDP-порты. Восстановление нельзя запускать поверх другой рабочей конфигурации.

Установите базовые зависимости на каждом VPS:

```bash
sudo apt update
sudo apt install -y curl ca-certificates python3 gnupg tar iproute2 openssl
```

Nginx устанавливайте **только при необходимости**, если его ещё нет:

```bash
sudo apt install -y nginx
```

## 3. Установка менеджера

Эти команды одинаковые для старого и нового VPS.

### Шаг 1. Подключитесь по SSH

```bash
ssh root@SERVER_IP
```

Вместо `SERVER_IP` используйте IP своего VPS.

### Шаг 2. Скачайте установщик из GitHub

```bash
curl -fL https://raw.githubusercontent.com/djekk9-ops/3XUI-MIGRATION/main/setup.sh -o /tmp/3xui-setup.sh
```

### Шаг 3. Проверьте файл **перед запуском от root**

```bash
bash -n /tmp/3xui-setup.sh
less /tmp/3xui-setup.sh
```

Для выхода из `less` нажмите `q`. При регулярном использовании лучше закрепить проверенный тег или хеш коммита вместо изменяемой ветки `main`.

### Шаг 4. Установите программу без автоматического запуска меню

```bash
sudo bash /tmp/3xui-setup.sh --repo djekk9-ops/3XUI-MIGRATION --ref main --no-run
```

Скрипты помещаются в `/opt/3xui-migration/`. Создаётся команда `3xui-migrate`.

> Установка **только менеджера** не заменяет базу 3x-ui и не применяет Nginx. Изменяющие систему действия запускаются отдельно из меню.

### Шаг 5. Откройте меню

```bash
sudo 3xui-migrate
```

Или напрямую:

```bash
sudo bash /opt/3xui-migration/menu.sh
```

## 5. Резервное копирование старого VPS

**Все команды этого раздела выполняются на исходном сервере.**

### Шаг 1. Откройте менеджер

```bash
sudo 3xui-migrate
```

Выберите пункт `1`. Либо запустите копирование напрямую:

```bash
sudo bash /opt/3xui-migration/backup.sh
```

### Шаг 2. Создайте пароль для архива

Программа попросит ввести и повторить **отдельный пароль шифрования**. Символы при вводе не отображаются. Сохраните пароль: без него расшифровать архив не получится.

### Шаг 3. Запишите путь к созданному архиву

Пример сообщения:

```text
ГОТОВО: /root/3xui-backup-20261024-160000.tar.gz.gpg
```

Дата и время в имени будут другими. Проверить наличие файлов:

```bash
sudo ls -lh /root/3xui-backup-*.tar.gz.gpg
```

### Шаг 4. Скопируйте архив на свой компьютер

На **компьютере**, где доступен `scp`, выполните:

```bash
scp root@OLD_VPS_IP:/root/ИМЯ_АРХИВА.tar.gz.gpg .
```

Подставьте реальный адрес сервера и фактическое имя архива. Можно также использовать SFTP/WinSCP или файловый менеджер SSH-клиента.

> [!CAUTION]
> Архив содержит учётные данные 3x-ui, клиентские доступы и приватные ключи. Даже зашифрованный архив **не загружайте в публичный GitHub**. Храните его вне VPS и сохраняйте пароль отдельно.

## 6. Восстановление на новом VPS

> [!CAUTION]
> **Только новый/пустой VPS.** Не запускайте пункт `2` на текущем рабочем сервере. При восстановлении записывается база 3x-ui и копируются сертификаты. Старый VPS оставьте включённым.

### Шаг 1. Установите менеджер на новый VPS

Повторите [раздел 3](#3-установка-менеджера) на новом сервере.

### Шаг 2. Загрузите резервную копию на новый VPS

Скопируйте файл `*.tar.gz.gpg` в `/root/` нового VPS. Пример команды **с компьютера**:

```bash
scp ./ИМЯ_АРХИВА.tar.gz.gpg root@NEW_VPS_IP:/root/
```

Убедитесь, что файл есть:

```bash
sudo ls -lh /root/3xui-backup-*.tar.gz.gpg
```

### Шаг 3. Запустите восстановление

Через меню:

```bash
sudo 3xui-migrate
```

Выберите пункт `2` и укажите полный путь к зашифрованному архиву.

Или запустите напрямую:

```bash
sudo bash /opt/3xui-migration/restore.sh /root/ИМЯ_АРХИВА.tar.gz.gpg --same-domain
```

Программа запросит пароль, определит новый публичный IPv4, основной интерфейс и попросит указать прежний домен.

Если знаете домен заранее, можно передать его в аргументе:

```bash
sudo bash /opt/3xui-migration/restore.sh /root/ИМЯ_АРХИВА.tar.gz.gpg --same-domain --domain=YOUR_DOMAIN
```

### Шаг 4. Проверьте план изменений

Убедитесь, что новый IP, сетевой интерфейс и домен указаны правильно. Программа сообщит, что DNS и CDN автоматически не меняются, а клиентские ключи сохраняются.

Для продолжения нужно вручную ввести:

```text
ПЕРЕНОС
```

После подтверждения скрипт устанавливает 3x-ui при отсутствии, восстанавливает базу и сертификаты, а Nginx **только подготавливает**.

### Шаг 5. Если автоматическое определение IP не удалось

Сначала проверьте публичный IP нового сервера. При необходимости можно явно указать его:

```bash
sudo env PUBLIC_IP=NEW_VPS_IP bash /opt/3xui-migration/restore.sh /root/ИМЯ_АРХИВА.tar.gz.gpg --same-domain
```

Здесь `NEW_VPS_IP` — реальный публичный IPv4, **не внутренний адрес** вроде `10.x.x.x`.

### Шаг 6. Проверьте результат

```bash
sudo systemctl status x-ui --no-pager
sudo ss -lntup
sudo cat /root/3xui-migration-staged/adaptation.json
```

Отчёт показывает изменения распознанных адресных полей и предупреждения. Если какая-то настройка не адаптировалась, её нужно проверить вручную.

## 7. Проверка IP, DNS, TLS и Nginx

### 7.1. IP и сетевой интерфейс

```bash
ip -4 route show default
curl -4 https://api.ipify.org
```

Убедитесь, что используются интерфейс и публичный IP нового сервера.

### 7.2. DNS и CDN

Проверьте, что домен указывает на нужный сервер:

```bash
getent ahostsv4 YOUR_DOMAIN
```

При переносе с прежним доменом нужно обновить A-запись у DNS-провайдера. Если используется CDN, отдельно проверьте адрес origin. **Скрипт не меняет DNS или CDN автоматически.**

> [!TIP]
> Переключайте основной DNS только после подготовки нового сервера. Если у пользователей уже есть сохранённые IP-адреса или ссылки подписки с IP, их может понадобиться обновить отдельно.

### 7.3. TLS-сертификат

Замените `YOUR_DOMAIN` на свой домен:

```bash
sudo openssl x509 -in /etc/letsencrypt/live/YOUR_DOMAIN/fullchain.pem -noout -dates
```

Проверьте срок действия сертификата и настройки его продления. Копирование файлов Let's Encrypt само по себе **не подтверждает**, что автоматическое продление настроено и работает.

### 7.4. Подготовленный Nginx

После восстановления сохранённая конфигурация находится здесь:

```text
/root/3xui-migration-staged/nginx/
```

Посмотрите её содержимое:

```bash
sudo ls -la /root/3xui-migration-staged/nginx/
```

Проверьте `server_name`, `proxy_pass`, пути TLS, порты, XHTTP/WS и отсутствие конфликтов.

> [!WARNING]
> Применение Nginx заменяет **всю** конфигурацию `/etc/nginx` на новом VPS. Не запускайте его на действующем сервере без проверки.

Если Nginx ещё не установлен:

```bash
sudo apt install -y nginx
```

После проверки примените подготовленную конфигурацию через пункт `5` меню либо командой:

```bash
sudo bash /opt/3xui-migration/apply-nginx.sh
```

Для подтверждения введите `NGINX`. Затем проверьте:

```bash
sudo nginx -t
sudo systemctl status nginx --no-pager
```

### 7.5. Проверка клиентских подключений

После переноса обновите подписку в VPN-клиенте и отдельно проверьте:

1. Установление соединения и задержку.
2. Открытие сайтов и работу DNS.
3. Скачивание и отправку данных.
4. Работу TCP- и UDP-протоколов.
5. Доступность подключения через мобильную сеть и Wi-Fi.

**Не отключайте старый VPS до завершения этих проверок.**

## 8. Диагностика неполадок

| Проблема | Что проверить |
| --- | --- |
| `3xui-migrate: command not found` | `command -v 3xui-migrate`; альтернативно `sudo bash /opt/3xui-migration/menu.sh` |
| GitHub недоступен | Интернет, DNS и доступ к `raw.githubusercontent.com` |
| Нет базы для резервного копирования | Наличие `/etc/x-ui/x-ui.db` |
| Архив не найден | Путь, имя файла и `sudo ls -lh /root/*.gpg` |
| GPG не расшифровывает архив | Правильность пароля и целостность файла |
| x-ui не запускается | Журнал `journalctl -u x-ui -n 100 --no-pager` |
| Nginx не запускается | `nginx -t`, сертификаты и конфликты портов |
| VPN подключается без интернета | DNS, firewall, интерфейс, маршрутизация, TLS и исходящие правила |

Быстрая проверка служб:

```bash
sudo systemctl status x-ui --no-pager
sudo systemctl status nginx --no-pager
sudo ss -lntup
```

Проверка логов:

```bash
sudo journalctl -u x-ui -n 100 --no-pager
sudo journalctl -u nginx -n 100 --no-pager
```

У самого менеджера есть режим диагностики: откройте `sudo 3xui-migrate` и выберите пункт `3`.

## 9. Обновление менеджера

Скачайте актуальную версию `setup.sh` и **проверьте изменения**, прежде чем запускать её с правами root:

```bash
curl -fL https://raw.githubusercontent.com/djekk9-ops/3XUI-MIGRATION/main/setup.sh -o /tmp/3xui-setup.sh
bash -n /tmp/3xui-setup.sh
less /tmp/3xui-setup.sh
```

Для обновления программных файлов:

```bash
sudo bash /tmp/3xui-setup.sh --repo djekk9-ops/3XUI-MIGRATION --ref main --update --no-run
```

Предыдущий каталог менеджера будет переименован с временной меткой. Это **не** обновляет саму панель 3x-ui и не выполняет миграцию базы.

## 10. Файлы проекта и безопасность

```text
3XUI-MIGRATION/
├── setup.sh          # загрузка и установка менеджера
├── menu.sh           # русское меню
├── backup.sh         # резервное копирование с GPG

├── adapt_db.py       # адаптация полей SQLite
├── hostinfo.py       # определение публичного IP и интерфейса
├── db_guard.py       # полная проверка и нормализация SQLite
├── test_db_guard.py  # тесты проверки базы
└── README.md         # этот документ
```

### Никогда не загружайте в публичный репозиторий

- Базы данных 3x-ui (`x-ui.db`, `.sqlite`).
- Резервные копии (`*.gpg`, `*.tar.gz`).
- Приватные ключи TLS, Reality и AmneziaWG.
- Пароли и токены доступа.
- Персональные ссылки подписок.
- Экспортированные конфигурации клиентов с секретами.

Рекомендуемый `.gitignore`:

```gitignore
*.gpg
*.db
*.sqlite
*.sqlite3
*.pem
*.key
*.env
*.log
3xui-backup-*
.env
```

> [!CAUTION]
> `.gitignore` не удаляет уже опубликованные данные, не защищает историю коммитов и не блокирует ручную загрузку файлов через сайт GitHub. Если секрет попал в публичный репозиторий, его нужно заменить и отдельно разобраться с историей публикации.

### Важные ограничения

- Полное восстановление на новом реальном VPS ещё требует практического тестирования.
- Настройки, которые хранятся **вне базы 3x-ui** и перечисленных каталогов, могут не переноситься.
- Сертификаты и доменные настройки привязаны к прежнему домену.
- Скрипт не генерирует новые секретные ключи и не меняет их автоматически.
- Автоматическая адаптация IP выполняется только в распознанных полях.
- Работу подписки, обратного прокси, CDN, firewall и сертификатов нужно проверить отдельно.

## Изменения v2.2 (кандидат, требуется повторное испытание)

- Полная проверка SQLite (`PRAGMA integrity_check`) перед переносом и после запуска 3x-ui; нормализация через SQLite backup API, сохранение старой базы и откат при обнаружении проблемы.
- В восстановленной базе на новом VPS отключается Telegram-бот (`tgBotEnable=false`), чтобы не конфликтовать со старым VPS. Токен сохраняется.
- Если архив содержит конфигурацию Nginx, а Nginx на новом VPS отсутствует, пакет устанавливается после подтверждения миграции. Конфигурация включается отдельно, с подтверждением.
- При применении Nginx источником служат активные сайты из `sites-enabled`, даже если они были самостоятельными файлами; выполняются проверка размеров и хешей, `nginx -t`, `nginx -T`, проверка порта 443 и откат при сбое.
- Успех восстановления объявляется только после подтверждения работы `x-ui` и целостности базы; перенос на занятый VPS блокируется.

**Перед использованием на продакшене:** повторите полный сценарий резервное копирование → перенос → восстановление → Nginx → VPN-тесты на отдельном чистом VPS. Никакие DNS-записи автоматически не изменяются.

Локальные проверки:

```bash
bash -n setup.sh menu.sh backup.sh restore.sh apply-nginx.sh check.sh
python3 test_db_guard.py
```
